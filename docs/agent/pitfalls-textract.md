# Textract（日本語・東京）と OCR ワークフローの罠
> このファイルはリポジトリに含まれる（GitHub から読める）。ローカルの Kiro では
> `.kiro/steering/pitfalls-textract.md` が読み込み条件だけを持ち、
> 該当する作業をしているときにこの内容へ誘導する。`.kiro/` は公開しないため、
> 知識の本体は常にこちら側に置く。

対象は `solutions/genai/japanese-document-ocr-agent/` と `shared/textract_helper.py`。
日付と環境は実測したもので、ap-northeast-1、2026-11-03 を指す。機能の対応状況は変わるため、
書く前に What's New と Developer Guide を引き直す。

| Pitfall | Solution |
|---------|----------|
| Forms を日本語の文書に使う | 公式ドキュメントは日本語を非対応としている（[E-016]）。実測ではリクエストは通り、請求書で 13 組、メモで 10 組を返したが、メモは文を途中で分けた組（信頼度 53.7）だった。使わず、項目は Bedrock で取る |
| Queries に日本語の質問を渡す | `InvalidParameterException`（実測） |
| 東京で AnalyzeExpense / AnalyzeID を呼ぶ | `AccessDeniedException`（not allow listed。発表でも未提供、[E-015]）。AWS Knowledge MCP の `get_regional_availability` は利用可と答えたので出典にしない。直接呼んで確かめる |
| S3 Access Points を Textract に参照で渡す | 読めない。同期は bytes を inline で渡し（5 MiB まで）、非同期は同じリージョンの一時バケットへコピーしてから `Start*` を呼ぶ |
| 一時コピーが残る | 終端のすべての経路で消す。`AsyncCheck` が失敗しても `AsyncCollect` へ進めて削除する（ASL の Catch）。1 日のライフサイクルは保険 |
| 非同期ジョブを取り消そうとする | 取り消す API がない（[E-018]）。`AsyncJobMaxSeconds` で待つのをやめても、ジョブは走り続けて課金されうる |
| 画像でも PDF でもないオブジェクトの扱い | `Start*` は受け付け、最初の `Get*` で `FAILED`（`INVALID_IMAGE_TYPE`）になる。同期は `UnsupportedDocumentException`。どちらも再試行せず失敗レコードで返す |
| 同期 API の 1 TPS（東京） | 20 回の連続呼び出しで、リトライなしは並列 2 で 4 回、並列 5 で 7 回スロットリングされた。adaptive（最大 5 回）は並列 1、2、5 とも 0 回で、実効 TPS は 0.56〜0.74。`MapConcurrency` は 2 から始める |
| 信頼度を自動承認の唯一の条件にする | 信頼度は誤りの有無をどちらにも示さない。誤りが 0 の 3 ページ PDF で文字の 22.6% が信頼度 90 未満の行にあり、「括弧」を「括孤」と読んだ行は 98.2 だった。閾値は出発点で、自分の文書で測る |
| 実際の応答の癖を設計書の想像で扱う | 結合セル（`MERGED_CELL`、信頼度 45 前後）が表の下の合計行を飲み込んだ。`TABLE_FOOTER` が出る。Layout の子 LINE の順序は読む順序と一致しない。1 ページの応答には `Page` がない。全角記号は半角で返る。応答は録画して fixtures にする |
| 日本語特有の文字の変化 | `〜` は `~`、`→` は欠落、`①②③` は `1 2 3`、`梱` が `栖`。比較と検索の前に NFKC で正規化する |
| 項目抽出で、書かれていない項目に値を作る | 値と一緒に原文からの引用を返させ、NFKC と空白除去のうえで部分一致を確かめる。一致しないものは `grounded: false`。1 つでもあれば HUMAN_REVIEW。書かれていない項目も根拠なしに数えるので、`fields` はそのコレクションの全文書にある項目だけにする |
| 項目の値をエージェントに返す | 値は文書由来の文字列で、指示に見える文が入りうる。システムプロンプトで従わないよう伝える。文書に指示を書いた場合の挙動は未測定 |
| `shared/bedrock_helper.converse_text` を項目抽出に使う | 常に `temperature` を送る。`extract_json` は解析の失敗を隠す。項目抽出は自前で `converse` を呼び、`temperature` は `BEDROCK_TEMPERATURE` があるときだけ送る |

## Map の集計が 256 KiB を超える

Map が終わった時点の状態は、リクエスト、`discovery` の出力、文書ごとの結果を同時に持つ。
キーは `objects` と `processed` の両方に載るので、**最終の出力を切り詰めても Map の集計は守れない**。
実測の組み立てでは、キー約 900 バイトの 100 件で約 340 KB（項目抽出あり）になった。

- 文書ごとの記録は一定の小ささにする。項目抽出の値と根拠は S3 の `fields.json` に書き、状態には
  件数と参照だけを載せる。`report` が読み直す（元の実装は値と根拠を状態に載せていた。上限値の計算では、20 項目、名前 40 文字、値と根拠が各 200 文字の
  日本語で 1 文書あたり約 28 KB になり、数件で 256 KiB に届く。実機に出す前のレビューで見つけた）。
- `discovery` が文書数を `キーのバイト数 × 2 + 1,700`（`PER_DOCUMENT_BYTES`）の和で制限する。
  見積りが実際より小さくならないことは `tests/test_state_budget.py` が、実際のハンドラーの出力を
  最悪値で埋めて確かめる。最初の定数 1,300 は、そのテストで 1,575 に対して足りないと分かった。
- 「テストが通った」だけでは、この種の上限は守れない。記録を増やす変更は、このテストが落ちることで
  定数の見直しを要求する。

## 実行履歴イベント（Standard、上限 25,000）

Task は 5、Wait と Choice は 2、ポーリング 1 回（Wait、AsyncCheck、Choice）は 9。sync の文書は
13、async の文書は 20 + 9 × ポーリング回数、項目抽出ありで +5。待機は 5、10、15、20 秒のあと
30 秒刻みで、600 秒まで待つと約 23 回になる。100 文書の最悪値は約 23,200 で、これが
`MaxFilesPerExecution` の上限 100 の根拠。23 回に達する実行は再現しておらず、再試行の
イベントは含めていない。

## 判断に迷ったとき

- 「Textract の X は日本語で使えない」と書く前に、実際にそのリージョンの API を直接呼ぶ。この作業では
  Forms は通ったが品質が低く、AnalyzeExpense と AnalyzeID は通らなかった。結果が違う。
- 精度の数値を書くときは、文書の種類、枚数、リージョン、日付を併記する。4 件の架空文書の値を
  一般化しない。
- 実在のドキュメントがない Access Point に対しては、一覧と取得とコピーの削除までを確かめ、
  OCR の成功は「未確認」と書く。共有ボリュームへ検証用のファイルを書かない。
