# ベンダーの「できない」を主張するときの規律

<!-- allow:not-a-claim: 主張の文型そのものを引用して説明している行 -->
「AWS は X に対応していない」は**主張**である。設計の前提に据えるなら、根拠がその重さに
見合っていなければならない。この文書は、その照合を人の注意力ではなくゲートに任せるための
仕組みを説明する。

## この仕組みが生まれた失敗

1 セッションで 5 つ起きた。**どれもその瞬間は成功に見えていた。**

| # | 起きたこと |
|---|---|
| 1 | 「FSx for ONTAP S3 Access Points に CloudWatch メトリクスは無い」を、**2 ページに対する `S3` という 2 文字の選択的検索が `No matches` を返したこと**を根拠に主張した |
| 2 | その弱い読みを、確定した事実としてドキュメントに書いた |
| 3 | それを**公開リポジトリにコミットしようとしていた**（git 履歴は永続する） |
| 4 | ベンダーの制約が設計のブロッカーなのに、**ベンダーのドキュメントを読んでいなかった**。後で読んだら 2 度とも逆の答えが出た（メトリクスのページは次元を列挙しており不在は文書化されていた。「2 ページが矛盾している」という主張は、ページを開かずに検索スニペットを引いたもので、そのページには不可能と書いたことをやっている実例が載っていた） |
| 5 | **AWS に訊かずに「AWS ではできない」と断定し、機能改善要望も出さなかった。** このリポジトリには `docs/aws-feature-requests/` が既にあったのに使わなかった | <!-- allow:not-a-claim: 過去の失敗の記述であって、ここで主張しているわけではない -->

注意して書こう、という申し送りは次の締め切りに耐えない。**ゲートは耐える。**

## 仕組みの構成

| 部品 | 役割 |
|---|---|
| `docs/agent/evidence-ledger.json` | ベンダーの不能・制限・不可能を主張するすべての claim。tier、全文で読んだ出典、実行した観測、サポートへの照会状況、機能要望の状況を持つ |
| `scripts/check_evidence_claims.py` | 追跡対象の Markdown を走査し、根拠の付いていない不能主張で落ちる。レジャー自身の妥当性も検査する |
| `scripts/evidence_claims_baseline.json` | ゲート導入時点で既に存在していた行の指紋。**承認ではなくラチェット**（後述） |
| `scripts/aws_support_inquiry.py` | レジャーから本文を組み立てて AWS Support にケースを起票する。ケース番号は追跡対象に書かない |
| `.kiro/hooks/scripts/evidence_gate.py` | `git commit` / `git push` を検出したときだけ走り、赤なら `exit 2` で止める |
| `.github/workflows/validators.yml` | 同じ検査を CI でも走らせる（`.kiro/` は未追跡なので、フックは 1 台しか守らない） |

## tier — 4 語しかない

| tier | 意味 | ゲートが要求するもの |
|---|---|---|
| `documented` | ベンダーの文書がそう言っている | **`read: "full"` の出典が 1 つ以上。** 選択的検索の `No matches` は不在の根拠にならない |
| `verified` | ここで何かを実行して観測した | `observation`（環境と日付つき） |
| `hypothesis` | 隣接する事実から推論した。ベンダーは言っていない | — |
| `open` | どちらとも確立していない | — |

**`read: "snippet"` は拒否される。** 検索結果のスニペットは文脈を落とす。上の失敗 4 は
これで存在しない矛盾を作った。

## 中核の規則

```
premise: true  かつ  tier が hypothesis / open  かつ  support_inquiry.status が required
  → 失敗する
```

**設計が推論に乗っているのに誰もベンダーに訊いていない状態**を赤にする。抜け道は 3 つあり、
どれも「訊く」か「頼るのをやめる」かのどちらかである。

1. ベンダーのページを全文で読んで tier を上げる
2. `make support-inquiry-file ID=E-nnn CONFIRM=1` で訊く
3. `premise: false` にして、その主張に依拠するのをやめる

**文言を書き換えて検査を通すことは抜け道に含まれない。**

さらに: `support_inquiry.status` が `answered` なのに `feature_request.status` が `not-yet`
なら落ちる。**「無い」と回答されて何も出さないのが失敗 5 だった。**

## ラチェットである理由

ゲートを入れた時点で、**追跡対象の 281 文書・539 行**が既に不能主張として読めた。全部で落と
せば、ゲートは真っ先に無効化される類のものになる。だからベースラインに指紋を記録し、
**新しく増えるものだけを止める**。

- ベースラインは**縮めるのが仕事**。`make evidence-baseline` は、新たに例外化する各行が本当に
  ゲート導入以前のものだと判断してから走らせる
- **一致しなくなった指紋も落ちる**。行を編集して古い指紋を残せば、その行が戻ってきたときに穴が
  再び開く

## 行に根拠を付ける書き方

```markdown
FSx for ONTAP S3 Access Points にリクエスト単位のメトリクスは見当たらない [E-001]。
```

`[E-nnn]` はその行か 1 行上にあればよい（表や箇条書きはマーカーが 1 行上に来る）。
意図的に思弁として書くなら:

```markdown
おそらく将来的には対応しないと考えられる。 <!-- allow:unverified: 根拠のない見通しであることを明示 -->
```

**主張していない行には `allow:not-a-claim:` を使う。** 主張を説明する文書は、自分が引用した
例文で検出器に掛かる。この文書自身がそうだった（冒頭の「AWS は X に対応していない」という
文型の引用と、失敗の一覧に書いた過去の断定）。

```markdown
<!-- allow:not-a-claim: 主張の文型そのものを引用して説明している行 -->
「AWS は X に対応していない」は**主張**である。
```

2 つを使い分ける理由は、言っていることが違うからである。`unverified` は「根拠なく推測として
書いている」、`not-a-claim` は「そもそも主張していない」。前者を後者に使えば、主張していない
ものを推測だと申告することになる。**検出器を避けるために例文を書き換えない。** 文書を道具に
合わせて劣化させることになる。どちらも理由の記述を必須にしてあるので、例示と言い逃れは
diff で区別できる。

## ケース番号を追跡対象に書かない

このリポジトリは公開で、git 履歴は永続する。レジャーは**訊いたという事実と日付**だけを持ち、
**ケース番号は `support_inquiry.private_ref` が指す gitignore 済みのパス**に入る。
チェッカーはそのパスが実際に無視されていることを検査し、起票ツールは無視されていなければ
書き込みを拒否する。

`--detail-file` も同じ扱い（アカウント ID やリソース ID を本文に足すときの入口）。

## 起票が慎重な理由

サポートケースは AWS から見え、アカウントに紐づき、**送信を取り消せない**。だから
`--draft` が既定で、`--file` は `--confirm` なしでは動かない。サービスコードを推測しない
ためのガードもある（`subject_service` を書いたら `service_code` が必須。**推測で埋めるのは
このゲートが防ごうとしている行為そのもの**）。

Support API は Business / Enterprise On-Ramp / Enterprise が必要。使えないアカウントでは
その旨を出して止まり、コンソールで訊いた後に手でステータスを更新する運用になる。

## 使い方

```bash
make check-evidence                                   # ゲートを走らせる
make support-inquiry                                  # どの claim が赤か
make support-inquiry-draft ID=E-001                   # 送る本文を読む（送らない）
make support-inquiry-file  ID=E-001 CONFIRM=1         # 起票する
make support-inquiry-list                             # このツールで起票したケース
python3 scripts/check_evidence_claims.py --self-test  # 検出器が実際に反応するか
make evidence-baseline                                # ベースライン再記録（慎重に）
```

## この仕組みが保証しないこと

**慎重な主張と不注意な主張は区別できない。** できるのは、不注意な主張を根拠なしに残せなく
すること、そして誰もベンダーに確認していない前提を声を出して失敗させることだけである。

そして**検出器はパターンと走査範囲の両方で沈黙する**。最初の版は受動形の `提供されていない`
しか見ておらず、能動形の `提供していない` を見逃した。見つけたのは再読ではなくテストだった。
危険な型を 1 つ見つけたら、同型を一巡すること。
