# 4 機能の先へ — 何を足すと何が要るか

> 🌐 **Language / 言語**: 日本語 | [English](../en/portal-parity-next-steps.md)

## TL;DR

- [同じ 4 機能を 3 つの構築ツールで実装した記録](portal-parity-four-features.md)で作ったのは、
  サインイン / 一覧 / 読み取り / アップロードの 4 つだけである。この文書は、**その先に何を足すと
  何が新しく必要になるか**をフェーズごとに書いたもので、読む人が自分の要件に必要なフェーズまで進めるように
  している。
- フェーズは 6 つある。**フェーズ 1〜3 は VPC 接続を要らない**。フェーズ 4 以降は
  Amazon FSx for NetApp ONTAP の管理 LIF に届く必要があり、**そこで Lambda を VPC に置く判断が
  発生する**。これは機能の難易度ではなく、到達できるネットワークの違いである。
- **最初に決めるべきはフェーズの数ではなく、書き込みの範囲と監査の要否**である。読み取り専用のまま
  フェーズ 3 まで行くのと、フェーズ 1 から書き込みを許すのでは、後戻りのコストが大きく違う。
- 費用はフェーズ 4 で不連続に増える。VPC エンドポイントか NAT Gateway が要るためで、
  トラフィックに関係なく月額が乗る。概算は[フェーズごとの費用](#フェーズごとの費用の増分)にある。
- どのフェーズでも共通して、**書き込みを prefix で限定する判断は最初に入れておく**。後から狭めるのは、
  すでに書かれたオブジェクトの移動を伴う。

## この文書の範囲

**書くこと**: 4 機能の先のフェーズ、各フェーズで新しく必要になるもの（権限・ネットワーク・リソース・
運用作業）、費用の増分の方向、フェーズを飛ばせる条件と飛ばせない条件。

**書かないこと**: 各フェーズの実装コード（このリポジトリの該当パターンへリンクする）。
性能や規模の見積り。構築ツールごとの優劣。

**対象読者**: 4 機能が動いた状態から、自分の要件に必要なところまで進めたい人。
どこで VPC が必要になるのか、どこで費用が跳ねるのかを先に知りたい人。

## フェーズの一覧

| フェーズ | 足すもの | VPC 接続 | 新しく要るもの |
|---|---|---|---|
| 1 | ページング・検索・並び替え | 不要 | なし（S3 の `ContinuationToken` だけ） |
| 2 | ダウンロードと共有リンク | 不要 | presigned URL の発行と有効期限の方針 |
| 3 | 大きいファイルのアップロード | 不要 | マルチパートアップロード、または presigned URL で直接送る経路 |
| 4 | ONTAP の情報表示（ボリューム・スナップショット・容量） | **必要** | 管理 LIF への到達、資格情報の保管、VPC 内 Lambda |
| 5 | ONTAP の操作（スナップショット作成・FlexClone・ロック） | **必要** | フェーズ 4 の全部 + 不可逆操作の承認フロー + 監査ログ |
| 6 | AI 処理（分類・要約・抽出） | 対象による | 推論の呼び出し、確信度の閾値、人間のレビュー、データ分類ラベル |

フェーズ 4 が境界である。**フェーズ 3 までは S3 Access Point だけで完結する**が、フェーズ 4 以降は ONTAP の管理面に
届く必要がある。管理面に何が到達できるかは
[FSx for ONTAP の管理インターフェースの整理](fsx-ontap-management-interfaces.md)にある。

## フェーズ 1. ページング・検索・並び替え

4 機能の一覧は prefix 配下を上限つきで返すだけである。実運用では件数が上限を超える。

**新しく要るもの**: S3 の `ListObjectsV2` の `ContinuationToken` を往復させる状態管理。
検索は「一覧を取ってから絞る」か「prefix を細かく切る」かの選択で、前者は転送量、後者は
命名規約への依存が増える。

**要らないもの**: 追加の権限、追加のリソース、VPC 接続。

**先に決めること**: 並び替えを**サーバ側でやるか**。S3 の一覧はキーの辞書順で返るため、
サイズ順や更新日時順はページを跨いだ並び替えになる。全件取得を前提にしないなら、
並び替えは「今のページの中だけ」と明示する必要がある。

## フェーズ 2. ダウンロードと共有リンク

読み取りをページ内に描画するのではなく、ファイルとして取り出すフェーズ。

**新しく要るもの**: presigned URL の発行。発行する側の資格情報の権限で URL が有効になるため、
**発行者の権限が URL の権限になる**。有効期限の方針（分単位か時間単位か）と、
発行の記録を残すかどうかを決める。

**先に決めること**: URL を持っている人が誰かを問わないなら、それは**認証の外側に出る経路**である。
社外共有を許すなら、期限と失効の手段を先に決める。

このリポジトリの実装は
[S3 Access Point と ONTAP API の罠](../agent/pitfalls-s3ap-ontap.md)に、presigned URL の
署名バージョンとエンドポイント指定の注意を記録している。

## フェーズ 3. 大きいファイルのアップロード

4 機能のアップロードは本文を JSON で送る形で、API Gateway と Lambda のペイロード上限に当たる。

**新しく要るもの**: 次のどちらか。

- **マルチパートアップロード**をサーバ側で管理する（`CreateMultipartUpload` /
  `UploadPart` / `CompleteMultipartUpload`）。パートごとの進捗と、中断したアップロードの
  後片付けが必要になる
- **presigned URL でブラウザから直接送る**。サーバはペイロードを通らないので上限に当たらないが、
  prefix の限定を URL の発行時にしか強制できない

**先に決めること**: 書き込みの検証をどこでやるか。サーバを経由しない経路では、
**ファイル名と prefix の検査を発行時に済ませておく**しかない。

## フェーズ 4. ONTAP の情報表示

ここから性質が変わる。ボリュームの一覧、スナップショット、容量、ARP の状態などは
S3 Access Point からは見えず、ONTAP の REST API に問い合わせる。

**新しく要るもの**:

| 項目 | 内容 |
|---|---|
| ネットワーク | 管理 LIF はプライベートなので、**Lambda を VPC 内に置く**（または TGW ピア経由） |
| 資格情報 | ONTAP の管理ユーザーを AWS Secrets Manager に置き、ローテーションの方針を決める |
| 到達性 | VPC 内 Lambda から AWS の他サービスへ出るための VPC エンドポイントか NAT Gateway |
| 分離 | VPC 内の関数から Internet origin のアクセスポイントへ出るには egress の経路（NAT Gateway か エンドポイント）が必要。このリポジトリは経路を足すのではなく、ONTAP 用の VPC 内関数とアクセスポイント用の VPC 外関数に分けている |

最後の点は設計に効く。このリポジトリのポータルも同じ分離をしていて、
`AGENTS.md` に「単一の Lambda が管理 LIF と Internet-origin の S3 AP の両方に届くことはない」と
書いてある。フェーズ 4 に進むと、**関数の数ではなく関数の置き場所が増える**。

**費用が不連続に増えるのはここである**（[フェーズごとの費用](#フェーズごとの費用の増分)）。

**先に決めること**: 情報表示だけで止めるか、フェーズ 5 に進むか。表示だけなら読み取り専用の
ONTAP ユーザーで済み、権限の設計がずっと軽い。

## フェーズ 5. ONTAP の操作

スナップショットの作成、FlexClone、ボリュームのロックなど、状態を変える操作。

**新しく要るもの**: フェーズ 4 のすべてに加えて、

- **不可逆操作の承認**。スナップショットのロックと SnapLock の保持は一方向で、保持モードは
  ボリュームの作成時に固定され、ロックしたスナップショットの期限は延長だけができる。
  誰が要求し、誰が承認したかを操作の前に記録する経路が必要になる
- **監査ログ**。状態を変えた操作を、後から改変できない形で残す
- **失敗した操作の扱い**。ONTAP のジョブは非同期で、成功応答が完了を意味しない場合がある

**不可逆操作について**: このリポジトリは SnapLock と Tamperproof Snapshot に関して、
**API が成功を返してもリソースが変わらない場合**や、**監査ログのボリュームが親リソースの削除を
数か月ブロックする**ことを実測して記録している
（[SnapLock の罠](../agent/pitfalls-snaplock.md)）。フェーズ 5 を検討する時点で読んでおくとよい。

**先に決めること**: 誰がこのフェーズの操作をできるか。ロールと承認の設計は、実装より先に決まっていないと
後から入れられない（既に発行したトークンにロールが載っていないため）。

## フェーズ 6. AI 処理

分類、要約、抽出などをファイルに対して実行するフェーズ。

**新しく要るもの**:

| 項目 | 内容 |
|---|---|
| 推論の呼び出し | Amazon Bedrock などの呼び出し権限と、リージョンの選択 |
| 確信度の扱い | 出力を**そのまま採用しない**しきい値の設計 |
| 人間のレビュー | しきい値を下回った出力を人に回す経路 |
| データ分類 | 出力に分類ラベルを付け、入力の機微度を引き継ぐ |

**AI の出力は補助信号であって最終判断ではない。** 分類や抽出の結果をそのまま業務判断に使う設計は、
規制業種では成立しない。このリポジトリは `shared/human_review.py` で確信度に基づく分岐を、
`shared/data_classification.py` で出力のラベル付けを扱っている。

**先に決めること**: 誤りが出たときに誰が気づくか。しきい値を置いても、
下回った出力が誰にも回らない設計では意味がない。

## フェーズごとの費用の増分

金額は時点情報であり、リージョンと構成で変わる。**提示する前に現在の単価を確認すること。**
ここで示すのは増分の方向と、トラフィックに依存するかどうかである。

| フェーズ | 増分の性質 | トラフィック依存 |
|---|---|---|
| 1〜3 | S3 のリクエスト数と転送量が増える | **する**（使わなければ増えない） |
| 4 | **VPC エンドポイントまたは NAT Gateway の固定費が乗る** | **しない**（置いた時点から発生する） |
| 5 | フェーズ 4 と同じ。加えて FlexClone とスナップショットの容量 | 一部する |
| 6 | 推論のトークン課金 | **する** |

**フェーズ 4 が費用の段差である。** 1〜3 は「使った分」だが、4 以降は「置いてある分」が発生する。
検証のためにフェーズ 4 まで作ったなら、使い終わったら消す判断が必要になる。

このリポジトリの高コストリソースの概算と節約パターンは
[コストの考え方](../agent/cost-awareness.md)にある。

## フェーズを飛ばせる条件

| 飛ばしたいフェーズ | 飛ばせるか | 条件 |
|---|---|---|
| フェーズ 1（ページング） | 飛ばせる | 対象の prefix が明確に少件数だと分かっている場合のみ |
| フェーズ 2（ダウンロード） | 飛ばせる | ページ内表示で足りる用途（テキストや小さい画像） |
| フェーズ 3（大きいファイル） | 飛ばせる | 扱うファイルが API のペイロード上限より確実に小さい場合 |
| フェーズ 4（ONTAP 情報） | **飛ばせない** | フェーズ 5 の前提。管理面に届く経路がないと状態が読めない |
| フェーズ 5（ONTAP 操作） | 飛ばせる | ファイルの読み書きだけが要件なら不要 |
| フェーズ 6（AI） | 飛ばせる | 分類や要約が要件に入っていないなら不要 |

**フェーズ 4 だけが後から足しにくい。** ネットワークの配置と関数の分離に関わるため、
フェーズ 1〜3 の実装を書き換えることになる。フェーズ 5 以降を将来やる可能性があるなら、
**関数を「S3 AP に触るもの」と「ONTAP に触るもの」に分ける形を最初から取っておく**と、
後からフェーズ 4 を足すのが配線だけで済む。

## 構築ツールごとの向き

3 つの構築ツールのどれでも 6 フェーズすべてに到達できる。違いはフェーズを足すときの作業の性質である。

| | フェーズを足すときの作業 |
|---|---|
| AWS Blocks | ブロックの追加と、ブロックが grant する権限の確認。**外部リソースを参照する場合は権限を明示的に足す**（[T1](portal-parity-four-features.md#t1-filebucketfromexisting-が生成する-arn-の形式)） |
| Nx Plugin for AWS | ジェネレーターで project を足し、`ApplicationStack` に配線を書く。**手続きごとに Lambda が増える**ので、VPC 設定を足す対象も増える |
| Amplify Gen 2 | バックエンド定義に関数とリソースを足す。**VPC 内 Lambda はエスケープハッチで書く**ことになる |

いずれも「足せるか」ではなく「どこに書くか」の差である。選び方は
[構築ツールの選択肢](scaffolding-and-backend-toolkit-choices.md#選び方)にある。
